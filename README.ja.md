# Decision-Space Expansion（決断の前に選択肢空間を広げる）

> **Expand the option space before you decide.**
> 重要な決断の前に、まず選択肢空間を広げよ。

`decision-workbench` プロジェクトから抽出した意思決定メソッド。**重要な決断の前に、異種マルチモデルの委員会で選択肢空間を広げ、分岐を構造化し、現実の制約を回帰させて決断する——最終判断は必ず人間が行う。**

## なぜ必要か

- **決断力 = 選択肢空間の大きさ**であって、選ぶ能力ではない。自分の認知面が決断の上限になる。
- 単一モデル（または同一モデルの複数ロール）は自分の学習分布を再サンプリングするだけ。**真の分岐には異なるモデルファミリー**（Anthropic / OpenAI / DeepSeek / Google / ローカル OSS）が必要で、アンカリング防止のため互いに隔離して回答させる。
- モデルの意見の相違は post-hoc な理屈付け＋エコシステムバイアスであることが多いが、その**エコシステムの盲点こそ最も価値のある分岐**（例：中国圏モデルは ICP 届出・WeChat ミニアプリ・Aliyun を挙げ、海外モデルは AWS をデフォルトにする）。

## 3 段階ループ

### 1. 発散（選択肢を広げる）

- 同じブリーフを**異なるファミリーのモデル**に渡し、隔離して回答させる（互いに見えない状態＝アンカリング防止）。
- モデルごとに立場を割り当てる：アーキテクチャ / コスト / セキュリティ / プロダクト → 自然に案が分かれる。
- 異種モデルプールなら何でも良い：プロバイダ集約ゲートウェイ、複数 CLI（Claude Code / Codex / Gemini CLI / opencode）、ローカル Ollama / vLLM。重要なのは**モデルファミリーの多様性であって数ではない**。
- **必須の質問パターン：**
  - *「なぜ X を選ばなかったのか？」* — 除外した選択肢と理由を引き出す（情報密度最大）
  - *「主流ではないが、ちゃんとした理由のある選択肢を1つ挙げよ」* — モデルを学習分布の外へ蹴り出す
  - *「この案の最も脆い部分はどこか？」* — 単一モデルは自分自身への反対尋問をしない

### 2. 構造化（選択肢を分類する）

- **コンセンサス領域** → そのまま採用（標準解のある部分。例：整理券システムのステートマシン＋WebSocket）
- **真の分岐領域** → 人間の仲裁に値する
- **疑似分岐領域** → ノイズなので捨てる（例：CRUD システムの PHP vs Go は本質的差異ではない）

### 3. 収束（現実の制約で決断する）

- 現実の制約を回帰させる：予算、チームスキル、納期、市場/地域、コンプライアンス。**広げた選択肢空間の中**で AI に加重評価させる。
- 任意で `pyDecision`（AHP / TOPSIS / PROMETHEUS）を使い、選択肢を比較可能なスコア表にする。
- **最終判断は必ず人間。** モデルは自信満々に間違える。

## 核となる信念

- 決断力 = 選択肢空間の大きさ。自分の認知面が決断の上限である。
- モデルの意見の相違 = 学習データの地域/エコシステムバイアス ＋ post-hoc な理屈付けであって、深い推論ではない。最も価値があるのは地理/エコシステムの盲点の分岐。
- 同一モデルの複数ロールはロール多様性に過ぎず、認知的多様性は生まれない——異種モデルこそ真の分岐を生む。
- 委員会が広げるのは *known unknowns*。*unknown unknowns* には届かない——そして収束の過程で分岐を理解せざるを得なくなること**こそが認知の成長**。
- 最良の姿勢：*「何がわからないか」* がわからないときに AI に聞くのであって、*「何が欲しいか」* が決まっているときに AI にやらせるのではない。

## 落とし穴

- 委員会を「自動で最適解を出す機械」と見なさない——オープンな融合ツール（MoA / LLM-Blender）はデフォルトで AI 自身が答えを融合してしまい、**人間の仲裁ステップを消してしまう**。方向が逆。
- 疑似分岐は時間の無駄：モデルは割り当てられた立場に対し完全な理屈を捏造する（先に好み、後から理由）。
- 要件が選定を制約しないとき、モデルは自分が最もよく知るデフォルト値を出力する——最適解ではない。
- モデルは暗黙の制約（並行度、予算、チーム）を黙って仮定する——人間が実際の制約を埋め戻す必要がある。

## 出力テンプレート

意思決定レポートには次を含める：各案の骨格 → コンセンサス / 真の分岐 / 疑似分岐の領域 → 真の分岐それぞれのトレードオフ → 推奨＋却下理由 → 人間が判断すべき点を一言で。

## AI ツールへの導入

このリポジトリはメソッドを **Agent Skills 形式**（YAML frontmatter 付き単一 Markdown）で提供する。依存もコードも不要で、指示ファイルを読めるあらゆるツールで動作する。

| ツール | 配置場所 |
|---|---|
| **Claude Code** | `~/.claude/skills/decision-space-expansion/SKILL.md`（全体）または `.claude/skills/decision-space-expansion/SKILL.md`（プロジェクト単位） |
| **Cursor / Windsurf** | `.cursor/skills/decision-space-expansion/SKILL.md`、または `.cursor/rules/` |
| **OpenAI Codex** | コアメソッドを `AGENTS.md` に記載、または参照ドキュメントとして Codex に読ませる |
| **Gemini CLI** | `~/.gemini/skills/`（agent skills 対応） |
| **任意のエージェント / チャット** | SKILL.md の内容を貼り付ける、または `cat SKILL.md` して従う |

> 注：`SKILL.md` はツール非依存。「異なるモデルファミリー」は、各環境が到達可能なプール（集約ゲートウェイ、複数 CLI、ローカル Ollama/vLLM）に置き換えてよい——メソッド自体は変わらない。

## ファイル

- `README.md` — 英語版サマリー
- `README.ja.md` — 日本語版サマリー（本ファイル）
- `SKILL.md` — 完全なスキル定義（frontmatter + 本文）。Claude Code / Cursor / Codex / Gemini CLI / Hermes など Markdown を読めるエージェントが利用可能

関連：リファレンス実装は `decision-workbench` リポジトリ（FastAPI + React、mock ゼロキー、31 tests、hidden-gold eval: 単一モデル 26% → 素朴なマルチエージェント 78% → decision-workbench 100% / 12）。
